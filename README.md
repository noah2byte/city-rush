# 도심 질주

밤의 서울을 3바퀴 도는 3D 레이싱 게임이다. 라이벌 7대와 실시간으로 순위를 다투고, 부스터 패드와 커브의 원심력, 라이벌과의 몸싸움이 순위를 흔든다. 한 바퀴는 도심 업무지구·상가 거리·한강 다리·공원 대로·터널·항만 부두·고가도로·한옥 마을 중 5개 구역으로 이뤄지고, 레이스마다 코스가 바뀐다.

## 실행

```bash
npm install
npm run dev      # 첫 실행 시 외부 자산을 내려받아 가공한 뒤 개발 서버를 띄운다
npm run build    # dist/ 에 정적 파일 생성
npm run assets   # 외부 자산을 강제로 다시 받아 가공한다
```

## 조작

- ←/→ 또는 A/D: 조향 (커브에서는 바깥으로 밀리므로 반대로 꺾어 버틴다)
- ↑/W: 가속, ↓/S: 브레이크 (입력이 없어도 자동으로 가속한다)
- 주황 화살표 패드: 밟으면 잠시 최고 속도가 올라간다
- 모바일: 화면을 좌우로 끌어 조향, 가속은 자동

## 설계 메모

### 자산 관리

- **외부 자산은 git에 넣지 않고 스크립트로 재생성한다.** 바이너리가 이력에 쌓이지 않고, 어디서 받아 어떻게 가공했는지가 코드로 남아 라이선스 추적과 재현이 쉽기 때문이다.
- **원본 URL을 브랜치가 아닌 커밋 SHA로 고정했다.** 원본 저장소가 파일을 바꾸거나 지워도 같은 결과물을 얻기 위해서다.
- **`predev`/`prebuild` 훅에서 자산이 없을 때만 받는다.** 클론 직후 별도 단계 없이 바로 실행되게 하되, 매 빌드마다 네트워크를 타지 않게 하기 위해서다.
- **차량은 Khronos 공식 샘플 CarConcept(CC BY 4.0)를 썼다.** 실사 PBR 재질(클리어코트 도장, 유리 등)을 갖추면서 라이선스가 명확하고, 실존 브랜드 차량이 아니라 상표 문제가 없기 때문이다.
- **차량 모델을 11.8MB에서 1.4MB로 줄였다.** 10여 대를 동시에 그려야 하고, 뒤에서 보는 시점이라 폴리곤을 25%로 줄여도 차이가 잘 보이지 않기 때문이다. 압축은 디코더가 순수 JS라 wasm 파일 배포가 필요 없는 meshopt를 골랐다.
- **건물·도로·다리·터널·나무·컨테이너·크레인·한옥은 외부 자산 없이 코드로 생성한다.** 끝없이 이어지는 도시를 모델 몇 개로 반복하면 오히려 티가 나고, 창문 배치를 매번 무작위로 만드는 편이 더 자연스럽기 때문이다.

### 사실감

- **환경맵(HDRI)을 반사에 쓴다.** 차체 도장, 유리, 젖은 노면의 반사가 사실감에 가장 큰 영향을 주기 때문이다. 배경으로는 쓰지 않고 반사에만 쓴다.
- **건물 외벽 텍스처를 색상·발광·거칠기/금속성 세 장으로 나눴다.** 벽은 빛나지 않고 켜진 창만 빛나며, 유리만 매끈하게 반사하도록 하기 위해서다. 세 장이 같은 배치를 공유하도록 배치를 먼저 정한 뒤 그린다.
- **도로에 물웅덩이 모양의 거칠기 맵을 깔았다.** 젖은 곳만 반사가 번들거려 비 온 뒤 도심 느낌이 난다.
- **카메라 앞 54m 구간의 가로등·터널등에만 실제 광원(최대 5개)을 붙이고, 구간 가장자리에서는 세기를 서서히 줄인다.** 모든 가로등에 광원을 달면 비용이 광원 수에 비례해 늘고, 가장 가까운 가로등으로 광원을 순간 이동시키면 조명이 툭툭 바뀌어 화면이 깜빡이기 때문이다. 광원 개수는 고정해 셰이더 재컴파일도 피한다.
- **ACES 톤매핑과 높은 임계값의 블룸을 썼다.** 전조등·후미등·창문처럼 실제로 밝은 것만 자연스럽게 번지게 하기 위해서다.
- **안개를 지수(FogExp2)로 바꿨다.** 거리에 따라 선형으로 흐려지는 것보다 실제 대기 감쇠에 가깝다. 구역마다 농도를 달리해 다리는 멀리까지, 터널은 짧게 보인다.

### 레이스

- **폐곡선 서킷을 새로 만들지 않고, 구역 5개를 이은 한 바퀴를 반복하는 코스로 만들었다.** 직선 도로를 셰이더로 휘게 보이는 기존 구조와 도시 구역·날씨 연출을 그대로 살리기 위해서다. 바퀴 경계에 START·FINISH 현수막과 체커 라인을 둔다.
- **청크 위치로 난수 시드를 정한다(`rng.js`).** Math.random이면 바퀴마다 건물·이벤트가 달라져 "같은 코스를 돈다"는 느낌이 없다. 코스 시드를 섞어 레이스마다는 다른 코스가 된다.
- **커브에 원심력을 넣었다.** 곡률 × 속도² 만큼 바깥으로 밀어, 보기만 휘던 커브를 실제로 핸들을 꺾어 버텨야 하는 커브로 만든다. 판정은 여전히 직선 좌표계라 로직이 단순하다.
- **라이벌마다 최고 속도를 다르게 두고 러버밴딩을 건다.** 플레이어와 멀어지면 최고 속도를 ±7%까지 조절해, 누가 앞서든 금세 격차가 좁혀져 끝까지 순위가 뒤바뀐다. 가장 빠른 라이벌은 러버밴딩을 받으면 플레이어보다 빨라지므로, 이기려면 부스터와 커브 처리를 잘해야 한다.
- **라이벌은 앞이 막히면 빈 차선으로 옮기고, 일정 확률로 부스터 패드를 노린다.** 전부 같은 차선에서 줄지어 달리면 추월 장면이 생기지 않는다.
- **플레이어는 뒤쪽(6번째)에서 출발한다.** 앞에서 출발하면 추월할 일이 없어 순위 변동의 재미가 줄어든다.
- **부딪혀도 게임이 끝나지 않는다.** 서로 옆으로 튕기고 뒤차만 속도를 잃는다. 한 번의 실수로 레이스가 끝나면 3바퀴를 도는 동안 긴장보다 좌절이 커진다.
- **출발 직후 150m에는 부스터를 두지 않는다.** 8대가 몰린 구간에 패드가 있으면 패드를 두고 억울한 충돌이 난다.
- **순위가 바뀌면 숫자가 튀고(오르면 초록, 떨어지면 빨강), 올랐을 때만 "추월!"을 띄운다.** 떨어질 때마다 글자를 띄우면 화면이 시끄럽고 기분만 상한다.
- **꽃가루는 1등일 때만 터뜨린다.** 모든 순위에 주면 1등의 특별함이 사라진다. 3D 장면이 아닌 2D 캔버스에 그려 블룸·안개 영향을 받지 않게 했다.
- **결과표에서 아직 들어오지 않은 라이벌은 남은 거리와 현재 속도로 도착 시간을 예상해 보여준다.** 모두 들어올 때까지 기다리게 하지 않기 위해서다.

### 맵

- **월드를 24m 청크 단위로 스트리밍한다.** 앞쪽에 청크를 만들 때 그 위치의 구역에 맞는 건물·소품을 조립하므로, 같은 오브젝트를 되감아 재활용하던 이전 방식과 달리 달릴수록 풍경이 바뀐다. 청크 길이는 가로등 간격과 맞췄다.
- **구역 정의(`course.js`)와 조립 로직(`districts.js`)을 분리했다.** 새 구역은 `ZONES`에 한 줄, `builders`에 함수 하나를 추가하면 된다.
- **한 바퀴에 8개 구역 중 5개를 겹치지 않게 뽑는다.** 같은 풍경이 연달아 나오면 다채롭다는 느낌이 바로 깨지고, 5개면 한 바퀴가 약 2km라 3바퀴가 2분 남짓으로 끝난다.
- **구역 안에서도 교차로·도로 표지판·육교 같은 이벤트가 끼어든다.** 구역이 바뀌는 수백 m 사이에도 풍경에 변화를 주기 위해서다. 같은 이벤트가 붙어서 나오지 않게 최소 4청크(96m) 간격을 둔다.
- **도로 표지판에는 실제 서울 지명을 한글로 쓴다.** 추상적인 도시가 아니라 "서울을 달린다"는 느낌을 주는 가장 싼 방법이다. 캔버스에 웹폰트를 그려야 해서 폰트 로딩이 끝난 뒤 월드를 만든다.
- **고가도로는 도로를 들어 올리지 않고 주변 지면을 20m 내린다.** 도로·차량·판정은 전부 y=0 기준이라 주변만 내리는 편이 바꿀 코드가 적다.
- **보도를 구역마다 청크에서 만든다.** 한옥 마을은 박석, 고가도로는 방호벽, 교차로에서는 끊겨야 해서 고정 메시로는 표현할 수 없다.
- **컨테이너 더미는 박스 하나로 그린다.** 색이 다른 컨테이너 4단을 한 장의 텍스처에 그리고 쌓인 단수만큼만 보이게 반복을 조절했다. 컨테이너를 하나씩 메시로 만들면 야적장 하나에 드로콜이 수십 회 늘어난다.
- **청사초롱의 붉은 위·푸른 아래를 텍스처 한 장으로 칠했다.** 메시 두 개로 만들면 드로콜이 두 배가 되어 한옥 마을이 가장 무거운 구역이 됐다.
- **LED 전광판은 텍스처 오프셋만 흘린다.** 캔버스를 매 프레임 다시 그리면 텍스처 업로드 비용이 든다.
- **비는 구간 단위로 확률적으로 온다.** 오기 시작하면 빗줄기가 서서히 늘고, 노면 거칠기가 낮아져 반사가 늘고, 안개가 짙어진다. 터널은 지붕이 있어 비가 오지 않는다. 빗줄기 수는 고정하고 보이는 개수만 조절해 메모리 할당이 없다.
- **곡선과 언덕은 버텍스 셰이더로 화면에서만 휘게 만든다.** 도로를 실제로 굽히면 차량 이동과 충돌 판정을 곡선 좌표계로 다시 짜야 한다. 멀수록 더 많이 밀어내는 방식은 플레이어가 있는 z=0 근처의 변위가 0이라 판정 로직을 직선 그대로 둘 수 있다.
- **곡률과 안개 농도는 서서히 바꾼다.** 급변하면 도로가 순간적으로 꺾여 보여 멀미가 난다.
- **셰이더로 휜 메시는 프러스텀 컬링을 끈다.** 원래 위치 기준의 바운딩 스피어로는 휘어진 실제 화면 위치를 판단할 수 없어 멀쩡한 물체가 사라질 수 있기 때문이다.
- **차선을 도로 텍스처에 직접 그렸다.** 별도 메시로 두면 곡선 셰이더에서 도로와 따로 휘어 어긋나고 스크롤 비용도 든다.
- **구역에 들어설 때 이름을 잠깐 띄운다.** 풍경이 바뀌었다는 걸 알아차리게 하는 장치다.
- **주소에 `?zone=bridge&weather=rain`처럼 붙이면 해당 구역·날씨로 시작한다.** 구역별로 작업하고 확인할 때 매번 거기까지 달려가지 않기 위해서다. (구역: `downtown`, `shopping`, `bridge`, `park`, `tunnel`, `port`, `elevated`, `hanok` / 날씨: `rain`, `clear`)
- **HDRI의 최대 밝기를 잘라서 쓴다.** HDRI 속 점광원이 수면·젖은 노면에 비치면, 무한히 먼 환경맵 반사 특성 때문에 카메라를 따라다니는 빛덩이로 보였다.

### 성능

주소 끝에 `#debug`를 붙이면 FPS, 드로콜, 삼각형 수, 해상도 배율을 화면에 띄우고, 콘솔에서 `window.__game`으로 장면에 접근할 수 있다.

- **차량 부품 메시를 재질별로 병합한다.** 원본은 부품별 메시가 97개라 차 한 대가 드로콜 97회였고, 차 10여 대면 천 회를 넘어 CPU가 병목이었다. 병합 후 한 프레임 드로콜은 후처리 포함 약 290회다.
- **보이지 않는 실내·하부 부품은 병합에서 뺀다.** 추격 시점에서는 보이지 않는데 정점과 드로콜만 차지하기 때문이다.
- **차창의 투과(transmission) 재질을 일반 반투명으로 바꿨다.** 투과 재질이 하나라도 있으면 three.js가 매 프레임 장면 전체를 한 번 더 렌더링하기 때문이다.
- **청크의 건물·소품은 버리지 않고 풀에 돌려 재사용하고, 라이벌 차 7대는 처음에 한 번만 만든다.** 생성·삭제를 반복하면 GC가 주기적으로 돌아 순간 멈춤이 생기기 때문이다.
- **출발 전에 모든 차량 색과 셰이더를 미리 컴파일한다.** 주행 중 처음 등장하는 재질이 그 자리에서 컴파일되면 화면이 멈추기 때문이다.
- **렌더링 해상도를 프레임 시간에 따라 자동으로 조절한다(0.6~1.5배).** 버벅임보다 약간 흐린 화면이 낫기 때문이다. 해상도 변경 자체가 버퍼 재할당이라 쿨다운과 여유 폭을 둬 자주 바뀌지 않게 했다.
- **HUD는 값이 바뀔 때만 DOM을 갱신한다.** 매 프레임 innerHTML을 쓰면 레이아웃 계산이 반복된다.

### 움직임

- **조향을 두 단계 관성으로 계산한다.** 입력이 핸들 각을, 핸들 각이 옆 방향 속도를 서서히 따라가게 했다. 키를 누르는 순간 차가 목표로 끌려가던 이전 방식은 움직임이 딱딱하고 기계적이었다.
- **차머리 방향·기울기는 옆 방향 속도에서 파생한다.** 이미 매끄러운 값에서 나오므로 따로 흔들리지 않는다.
- **모든 보간을 지수 감쇠(`1 - exp(-k·dt)`)로 통일했다.** `min(1, dt·k)` 방식은 프레임 간격이 흔들리면 움직임도 같이 흔들린다.
- **카메라는 차보다 느린 감쇠로 따라간다.** 차가 화면 안에서 움직이는 여유가 생겨 속도감과 부드러움이 함께 산다.
- **최고 속도에 가까울수록 가속을 줄인다.** 공기 저항처럼 속도가 점점 무뎌져야 가속감이 자연스럽다.
- **터치 조향은 손가락까지 남은 거리에 비례해 핸들을 꺾는다.** 목표에 가까워지면 핸들이 저절로 풀려 지나치거나 흔들리지 않는다.

### 게임플레이

- **플레이어는 z=0에 고정하고 세상을 움직인다.** 좌표가 무한히 커지지 않아 부동소수점 오차가 쌓이지 않고, 충돌 판정이 단순해지기 때문이다.
- **모든 레이서는 코스상 절대 위치(m)를 갖고, 화면에는 플레이어와의 거리만큼 앞뒤로 그린다.** 순위는 달린 거리로, 완주한 레이서는 완주 시간으로 정한다.
- **차 크기와 앞 방향은 모델에서 자동으로 계산한다.** 차량 모델을 바꿔도 충돌 판정과 방향을 손으로 맞출 필요가 없게 하기 위해서다.
- **프레임 간격(dt)을 0.05초로 제한했다.** 탭 전환 후 dt가 커지면 한 프레임에 차를 통과해 충돌이 누락되기 때문이다.

## 배포

`main` 브랜치에 푸시하면 `.github/workflows/deploy.yml`이 빌드해서 GitHub Pages에 올린다. 결과는 `https://noah2byte.github.io/city-rush/`에서 볼 수 있다.

- **처음 한 번은 저장소 Settings → Pages → Source를 `GitHub Actions`로 바꿔야 한다.** 기본값인 브랜치 배포 방식은 빌드 결과물(`dist`)을 커밋해야 해서 쓰지 않는다.
- **`vite.config.js`의 `base`를 `./`로 둔 이유는 이 배포 때문이다.** 프로젝트 페이지는 `/city-rush/` 하위 경로로 서빙되므로 절대 경로로 빌드하면 에셋 경로가 깨진다.
- **블로그 글에는 iframe으로 임베드한다.** 게임과 블로그가 같은 출처(`noah2byte.github.io`)라 임베드 제약이 없다. 방향키가 바깥 페이지를 스크롤하지 않도록 게임 쪽에서 키 기본 동작을 막아뒀다.
